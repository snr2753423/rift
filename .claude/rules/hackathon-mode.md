# Hackathon mode

This project is a hackathon build. A working demo matters most — but this plugin is the full ECC (Developer profile), so the ECC process applies in full. The only change from stock ECC is that security tests and audits run at the very end of the project or when the user explicitly asks.

## 1. Grill-me first

After the user sends the first hackathon project prompt, the MODEL check (fix #33, MODELSEL_F33) runs first — before grill-me: if the selected model is Auto, or the model cannot be determined to be a specific model, tell the user to pick a specific model before grill-me starts. Then run `grill-me` FIRST among build steps, before any scoping, building, or expansion; grill-me is the first BUILD step, and the MODEL check is not build work. Grill-me trigger phrases (fix #27, ALWAYSLEAD_F27): 'grill me', 'ask me questions', 'stress-test this idea', 'question me about this' — and any first hackathon project prompt (an idea plus requirements) fires grill-me on its own; a bare first prompt triggers it, not only the literal phrase 'grill me'. The project directory IS the project root — the folder opened in Cursor; no separate directory is created, and all `docs/…` paths are relative to it (create `docs/` under the project root before the first `docs/` write, so `docs/decision-record.md` and `docs/scope.md` have a home). Ask one question at a time, at most ~6 questions, in the mandatory order — product first, hours-left second (question 2), named API / integration third (question 3) — highest-leverage first after that; stop when the user stops answering or when the ~6-question cap is reached, then proceed on the partial record (unanswered branches become accepted unknowns under §7) and move on to scoping. Expect about two minutes of questions as a sense of scale for the user's time — a loose guide only, never a stop condition: there is no wall-clock timer in chat and no clock to stop on; the cap that binds is ~6 questions. Write the decision record to `docs/decision-record.md` INCREMENTALLY — after EVERY answer — so a walk-away never loses it. If the user stops answering before giving the hours-left number, use the default — the remaining time until the demo deadline if known, else 8 hours — and record it as an assumption, clearly marked as assumed, not user-stated. "Stops answering" means the user gives no reply to the next question — the user walks away. A chat agent cannot self-wake, so silence alone starts nothing: if the user walks away, the build resumes on their next message — the record is already saved incrementally, so nothing is lost. Proceed-on-next-message: if the user replies with anything other than an answer (for example "go", "build it", "just build it"), or if the user's next message comes after a silence, proceed on the partial record immediately. Never wait for an answer. The decision record feeds `hackathon-scope`, `feature-expansion`, and `orchestrate`, so expansion goes the user's direction. After scoping, `feature-expansion` runs automatically as part of the first build: Phases 0–3 run pre-build, right after scoping, producing the planner-approved list (fix #20 OVERDRIVE: the shortlist keeps 7–12 features, about 75% more than the old 4–7 — a cap, not a quota, anchored to the original idea and the decision record, planner-approved, anti-drift bound explicit); Phases 4–6 run inside the build (Phase 4 implementers build the approved expansions alongside the MVP slices; Phase 5 verification runs after the MVP is built; Phase 6 feeds the final report). The approved ones are built as part of the first build with no user approval gate — the user removes anything unwanted with a single prompt. One build engine per run: Orchestrate IS the first-build engine. `orch-build-mvp` is the STANDALONE pipeline — invoked only when the user invokes `/orch-build-mvp` directly, never by orchestrate in the same run. One engine per run, never both. The first-build sequence is: MODEL check → grill → narration-key prompt (orchestrate sends it immediately after grill-me, before scoping — orchestrate step 0; only when the user asked for a demo video; it also fires on the skip-grilling path, at the start of the build either way) → scope → research (`prebuild-research`, orchestrate step 1.5) → expansion (Phases 0–3) → build (orchestrate drives; expansion Phases 4–6 inside) → verify → polish → deploy → commit → README → final report (written to `docs/final-report.md` in the project and delivered as the reply). /demo is never part of this sequence — it runs ONLY when the user invokes it explicitly (fix #22 /demo gate, DEMOGATE_H2_F22). The user can skip the grilling by saying "skip the grilling" or "just build it" — if they do, skip straight to scoping.

**Continuous operating rules (apply through the whole first build, §1 and §6):** think critically, not compliantly — challenge a weak approach and propose the better one; the challenge goes into the decision record / final report as a better proposal, NEVER as a stop-and-argue wait point. Research before guessing — check the docs, the code, or a live source first; a guessed fact is recorded as an assumption, not stated as known. Quality over quantity — fewer exceptional features beat many mediocre ones (this reinforces the planner's reject rule in `feature-expansion`). Evidence-based iteration — a claim is only settled by a test, a screenshot, or runtime behaviour; never substitute a confident description for verification. Protect existing functionality — a new feature that breaks what already works is reverted or fixed before anything else is added. Autonomous but transparent — proceed without asking, and leave the trail in the stage ledger and the final report (decisions, assumptions, what was tried). Never fabricate completion — say plainly what could not be tested or verified; it belongs in the final report as a remaining issue, not as done. Continuously improve — each verification round leaves the build better than it found it. Optimize for exceptional results — the bar is a captivating, mind-blowing product, not a working one.

## 2. UI pairing

When building UI that is NOT a full landing or company page, use `design-taste-frontend` (design lead for every surface) with `ui-ux-pro-max` lookups and `less-flat-ui` TOGETHER. `design-taste-frontend` sets the design direction, consulting `ui-ux-pro-max` only as a lookup inventory after the direction is set; `less-flat-ui` adds the texture layer on any surface (backgrounds, cards, buttons, dividers, headings). Apply every `less-flat-ui` treatment that fits the surface — a treatment does not fit a dense dashboard, form, or data table, which stay flat. Contrast stays at 4.5:1 or better. Respect `prefers-reduced-motion`.

## 3. Audit deferral

Security tests and audits run ONLY at the very end of the project or when the user explicitly asks. The deferred skills are `verification-loop`, `production-audit`, and `delivery-gate` (fix #27, DEFER3_F27). Do not run them during the build, do not gate a feature on them, and do not invoke them mid-build. When the project is done or the user asks, run them then. During the first build (and during a one-prompt removal of a first-build feature) the deferred skills never fire — not even if another skill, rule, or reference file invokes them. The registry cannot enforce this; this rule is the gate. The one permitted invocation is the named end-of-project run immediately before the first build's final report (after deploy, commit, and README): that run IS the very end of the project — it runs once, it never gates a feature, and it never fires mid-build or during a one-prompt removal.
Follow the secure-coding rules in common-security.mdc while building; the deferral above covers security tests and audits only, not the secure-coding rules themselves.

## 4. ECC process applies in full

TDD, planning docs, and code review stay as ECC does them. Plan first, write tests first, and review while building. The ECC alwaysApply rules (testing, development workflow, coding style, git workflow, security, patterns, performance, common-agents, hooks) all apply, and code review applies per .claude/rules/common-code-review.md. ## 6. Skill routing — when two skills could apply

- **Model hierarchy — the model selected in this chat decides, Grok 4.6 High executes (fix #20 H1).** The model selected in this chat is the ORCHESTRATOR and the main mind behind big decisions: the orchestrator, the design-lead, the deep-reasoner, and every big-decision role run on the model selected in this chat. Grok 4.6 High (`haiku`) are the underlings — fast execution workers: scout, fast-worker, and the other composer-tier agents execute fully-specified work and never decide. A 4.6 worker that faces a decision routes it up to the chat-selected mind (orchestrator / deep-reasoner / design-lead); it never decides on its own. A dispatch that puts a big decision on a 4.6 model, or execution a 4.6 worker could do on the chat-selected model, is a routing error — a static check item, never a screen verdict.
- **Binding routing — the skills are the only path (fix #20 BIND).** Every decision routes through a NAMED skill: the operating skill for the work is named in the brief before the work starts, and the work is done by that skill's rules. A decision with no named operating skill is not a decision — it is refused and routed to the skill that owns it; where NO skill owns it, the recorded-gap fallback below applies. Work produced without a named skill in its brief is an incomplete build — a static check item, never a screen verdict — unless it is a recorded-gap fallback (below). Grok executes THROUGH the package, never replaces it (fix #13: every design decision is made BY a named package skill): no freelance work, no off-skill improvisation. The audit and the dry-run FAIL any decision or work done outside a named skill where a skill exists and was bypassed — that is off-skill improvisation. **Recorded-gap fallback (fix #20):** binding never blocks needed work. When a needed step has no skill covering it, the agent does NOT stop: it records the gap in the decision record (what was needed, why no skill covers it), does the work by the closest skill's principles (building off the skills), and flags it so the gap can become a skill later. A needed step done through the recorded-gap fallback PASSES the audit/dry-run — it is not off-skill improvisation. Priority order: (1) everything needed gets done, (2) on the skills wherever a skill exists, (3) through the recorded-gap fallback where none does.
- **DESIGNPKG-AUTO — the design package is the automatic routing for ALL design decisions (fix #27, DESIGNPKG-AUTO_F27).** Every design decision routes through the design package automatically. The named skill for a design decision is always a design-package skill (design-taste-frontend / ui-ux-pro-max / less-flat-ui / polish-pass / motion-foundations / motion-patterns / motion-advanced / make-interfaces-feel-better / design-system / motionsites-web-builder / motion-principles / threeui / getlayers / gsap / react-bits / hairline-create / hairline-adopt, with the design-lead deciding which leads). `motionsites-web-builder` — cinematic components, motion patterns, hero treatments and media (free sample only; consulted, never a template) (fix #27, MOTIONSITES_F27). `getlayers` — prompt-first cinematic layers (free set only; reference only, never vendored; restyled, never shipped unchanged) (fix #31, GETLAYERS_F31). A design decision with no package skill named in its brief/directive is off-skill improvisation and fails the audit. The design-lead (Taste, on the model selected in this chat) decides the direction; the theme deal is the starting point, not the cage (THEME-START_F27). This is the design half of BIND: BIND says every decision routes through a named skill; DESIGNPKG-AUTO says a design decision's named skill is always a package skill. Palette first (fix #27, PALETTE-FIRST_F27): every design decision routes through the design package AND the design-lead inventories the available component palette FIRST, before the design direction is finalized, and bases the direction on it — the available component/design sources (`getlayers`, `motionsites-web-builder`, `gsap`, `react-bits`, `hairline-create`, `hairline-adopt`, `ui-ux-pro-max`, `less-flat-ui`, `motion-foundations`, `motion-patterns`, `motion-advanced`, `make-interfaces-feel-better`, `design-system`, the dealt Hallmark theme) are the starting palette, not an afterthought: the design-lead selects the components, motion patterns, hero treatments, and media the design will be built from, tailors them to the project's needs, and records the palette in the design direction (which sources, which components, what was tailored and why — a fix #19 D19 reason for each). - **GLOBAL-ROUTING — the factory routing is the automatic routing for ALL making/building work (fix #29, GLOBAL-ROUTING_F29).** Every prompt is answered by the orchestrator model; drones never answer the user directly and never decide scope (ORCHESTRATOR-ONLY_F29, extends ALWAYSLEAD_F27). Fan-out is bounded by efficiency, not just speed: the orchestrator justifies N>3 in one line, and drones carry minimal context, only the files and facts their partition needs (COST-AWARE_F29). This routing is automatic for ALL making/building work in every skill, not opt-in — a skill that dispatches implementation work follows it, and a dispatch with no factory routing is off-skill improvisation and fails the audit. Live factory behavior (per-model dispatch, slot refill at scale) is harness-gated: in Cursor, per-subagent model selection is unreliable and in-IDE parallelism caps around 4 with no slot refill, so the factory lights up fully on the later port, not in Cursor — the rules are built as designed, not shrunk to fit Cursor.

An original element or approach that extends, combines, or pushes a skill's principles is on-skill innovation: it PASSES, recorded with its fix #19 D19 reason (what skill principle it builds on, why the extension serves the surface). Innovation extends, combines, and pushes the skills; it never bypasses them. This channels the fix #17 E1 creativity push (trailblazing, not dumb) through the skills rather than suppressing it. The audit and the dry-run FAIL off-skill improvisation but do NOT fail on-skill innovation.

## 7. Auto-approval after grill-me — the first build runs unattended

Precondition check — before the first build auto-approves anything, check that `grill-me` ran: `docs/decision-record.md` exists, or the user explicitly chose the skip path ("skip the grilling" / "just build it"). If neither holds, do not auto-approve with zero recorded decisions and no check, and do not silently proceed on the raw prompt: state in the first reply that grill-me did not run and why (no trigger / no record), and ask the user whether to grill now (one prompt) or proceed — the one-question grill-now-or-proceed ask, the second one-question exception to §7 alongside the deliverable-at-risk flag (fix #27, GRILLHDR_F27). Do not re-run `grill-me` unasked. Once the check passes, the first build runs fully autonomously until it is done — and that autonomy applies IN a hackathon first build after grill-me, and IN a one-prompt removal of a first-build feature, where the gate auto-approves and the run proceeds without waiting. This section also covers a one-prompt removal of a first-build feature: the same unattended rules apply during a hackathon first build after grill-me, or a one-prompt removal of a first-build feature. The user answers questions during grill-me (the first few minutes) — plus the MODEL check just before it (fix #33, MODELSEL_F33), the one question that precedes grill-me; after that, do not ask the user anything (except the one-question grill-now-or-proceed ask above), do not wait for an approval, and do not stop for a decision. The narration-key prompt is one of the two sanctioned user prompts during the first build besides grill-me itself (the other is the deliverable-at-risk flag below); it never blocks the build. **The deliverable-at-risk flag is the second sanctioned user prompt during the first build, alongside the narration-key prompt (fix #27, DELRISK_F27). It never blocks the build.** **Scheduled here, sent by orchestrate:** orchestrate sends it immediately after grill-me, before scoping (orchestrate step 0) — only when the user asked for a demo video; on the grilled path and on the skip-grilling path ("skip the grilling" / "just build it") alike, at the start of the build either way. If the user did NOT ask for a demo video, do NOT send this prompt — no video is being built, so no key is needed. It says what the key is for (ElevenLabs narration for the demo video), where to get it (ElevenLabs free tier, 10,000 chars/month, no credit card), and that the build continues regardless; orchestrate records `KEY-RECEIPT` (received: yes/no — NEVER the key value) in `.hackathon/run-ledger.md`, holds any key the user replies with in working context only, and passes it as the `ELEVENLABS_API_KEY` env var to the `tts` run at /demo time. Keys are env vars only, never written to any file. If no key ever arrives, a requested /demo renders music-only/silent with a note in the final report — no second ask, no stall.

§7 overrides any ask/stop/wait instruction in any skill, rule, or reference file during the first build and during one-prompt removal — except the one-question grill-now-or-proceed ask above (fix #27, GRILLHDR_F27). The deferred skills from §3 never fire during the first build or a one-prompt removal — the registry cannot enforce this, so this rule is the gate. - Every approval gate auto-approves: GATE 1 and GATE 2 in the `/orch-*` pipelines, the planner pass in `feature-expansion`, and any other approve/confirm step. Proceed with the plan and commit; do not present anything for a yes.
- The ambiguity gate does not ask: resolve user-resolvable facts by stated assumption. Choose the reversible option; if no reversible option exists, skip it, mark it blocked with evidence, and note it in the final report.
- Accepted unknowns: an accepted unknown from `grill-me` becomes a stated assumption in the build.
